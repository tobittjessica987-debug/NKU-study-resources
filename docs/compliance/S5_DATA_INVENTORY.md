## 决定边界

注销至少涉及四个独立事实：账号是否还能访问；业务资料是否仍关联账号；内容是否继续公开；受限证据和历史副本是否继续保留。清除一个登录字段不能证明另外三个已经完成。

本次盘点时，D-01（公开评价、普通反馈及公开回复保留还是退出公开）、私密投诉原文/联系方式/回复的处置、支付及捐助记录的处置、各分类适用保留期仍未决。以下动作依赖不是替用户决定内容取舍。任何后续决定须记录到固定候选的政策、确认文案和验收中。

用户安全日志、管理员审计、调取日志采用的400天是既有工程配置；Caddy模板为`9600h`。本文件不把400天、6个月或长期保存解释为统一法定期限，不新增法律结论，也不擅自缩短已实施的日志保存。

## 基线差异与公开身份路径

| 基线承诺/路径 | 真实差异或边界 |
| --- | --- |
| 默认政策“手机号即被删除或匿名化” | 原注销SQL没有处理`phone/phone_verified_at`；受限调取仍可按手机号和内容`user_id`找回账号及全部本人投稿 |
| 默认政策与原`/me/`提示“已发布内容保留但解除关联” | 两份业务JSON仍保留归属；原昵称保留后加后缀。仅清OpenID不等于解除业务归属 |
| 自助注销“不可恢复” | 已confirmed扫码票据仍可给原账号行签发新token；原手机号认证也仍有效。静态代码路径已确认，本文件不声称进行生产重现 |
| 原删除动作失败 | token删除、账号更新、收藏删除分步运行；后续失败可能造成部分完成而客户端只看到错误 |
| 头像URL清空 | 对象和绑定登记未清；一年公开缓存持续存在，不能代表头像删除 |
| 默认政策“昵称随评价公开展示” | 旧`publicReview`及v1`publicReviewDto`均不返昵称；评价详情显示楼层。捐赠公开昵称是另一个已明确展示的业务字段 |
| 公开反馈/评价的直接账号字段 | 旧及v1公共DTO未直接返`user_id/phone/openid/avatar/contact/helpfulBy`。正文和获准公开的reply可含自述身份/图片链接，保留时仍会显示 |
| 默认政策“举报需手机号”“所有公开内容先审核”“处理结果我的反馈可查” | 私密投诉可匿名；评价沿用配置自动规则；匿名投诉没有账号回复查询凭证。页面已有固定补充提示不能消除Markdown中的相反承诺 |
| 400天工程配置与默认“6个月” | 工程配置与默认告知不是同一描述；不得新增法律推断掩盖差异 |

基线在途写入还需纳入一致性：头像路由在认证后经历读取、审核及R2写入await，没有最终账号复核；评价等待JSON锁后重验规则但不重验账号。反馈已有锁内身份复核。清理后才落地的旧账号投稿/头像不能由注销作业遗漏。

## 本轮候选采样与局部完成

2026-10-07并行实施时静态采样到`mp-auth-service`已增加`deleted_at/assertActiveUser/isDeletionPending`；账号字段、token与同库收藏改为事务处理，昵称改不含原值的稳定随机占位以兼容旧唯一索引，并清手机号认证，签发/资料/密码等入口拒绝注销账号。`web-login-service`已增加`revokeForUser`，收藏操作增加生命周期检查。这些是当时工作树源码改动采样，未在本文件中认定已完成端到端接线、失败恢复或全部验收；主窗口后续验证及剩余JSON提交窗口见[S5基础阶段记录](S5_CHECKPOINT.md)。

独立前端变更只负责结果确认，不决定任何数据保留策略：

- [account-deletion-controller.js](../../src/lib/account-deletion-controller.js)要求输入“注销”及肯定的最后确认才发送一次POST；提交时锁定输入/按钮，重复点击不再发请求。
- 使用既有`requestUserJson`保持同源Cookie、`no-store`和有界超时；不改既有账号API helper。
- 仅严格`code === 0 && data.deleted === true`且非`ok:false`才调用成功导航。坏JSON、空包、401/5xx、断网和超时均为“尚未确认注销结果”，不称成功，也不自动重复POST。
- [me.astro](../../src/pages/me.astro)显示中性“请先查看当前注销说明；提交后按服务端结果显示”，不保留不实“解除关联”承诺；最终策略提示须由D-01决定后统一。
- 结果提示有`role=status/aria-live`；默认表单提交被阻止，只有上述确认流程可请求注销。

局部验证：`node --test test/account-deletion-controller.test.mjs test/user-submissions-controller.test.mjs`，15/15通过（其中新增注销测试7项）；`npm run build:fixtures`退出0，14个合成静态页面生成成功。只使用注入fetch与仓库合成fixture；未请求真实注销接口、未做生产/微信真机验证。测试结果不证明服务端已完成全部清理。

## 最小待决与后续一致性验收

在一个D-01决定中明确原已公开评价、普通反馈和公开reply的去留，并明确待审内容、私密投诉、支付及公开捐赠昵称的分类。受限证据/案件档案/备份的期限若尚未确认，保留明确待定及负责人事项；无需为每张表重复发起内容取舍问题。对保留方案应说明正文自述信息可能继续展示；对退出公开方案应验证不能被取消隐藏、旧草稿、备份或静态回退恢复。

后续服务端与整体候选验收至少覆盖：

1. 合成账号A/B，A的微信与网页会话、confirmed扫码、收藏、历史/未绑定头像、全部投稿状态、对他人评价的投票、私密投诉及捐助数据；A按决定处理，B数据不变。
2. 每个持久步骤及日志/远端头像步骤故障、重启恢复、重复请求与在途上传/投稿；不重新签发旧账号token，不在清理后留下新的归属数据。
3. 旧/v1公共API、本人API、受限账号/内容调取、全部日志归档、搜索与派生计数、静态HTML和缓存读回；私密投诉始终不公开。
4. 旧单条及整份JSON草稿在注销后冲突或拒绝，不能覆盖新归属/资格；注销前备份只能隔离恢复，核对注销状态后才能激活。
5. 默认privacy、已知旧保存版本及自定义运行覆盖、确认文案、最终API note与发布HTML相互一致；生产未读回事项单列，不用合成build代替。

任何一项策略或恢复/发布证据未完成时，不将S5全项标记完成；现实组织安排和其余类型欠账继续按原阶段台账处理。
