# NKUStudy 安全合规内部处理规程（SOP）

> 版本：v1.3（2026-10-08）。安全负责人及正式联系人为本项目用户本人；其他管理员已确认。本次申报仅主站 `nkustudy.top`，公司资料沿用受控原PDF及用户记录。C-20 已确认团队现行运营做法，下文不再要求提供电话、成员名单或逐人值班表；统一社会信用代码、负责人真实姓名及公司账户信息不写入公开Git。本文件按 S3/S4/S5 候选核对软件操作与人工处理职责，不是已处理真实案件、已部署候选或已通过安全评估的证明。

## 一、角色与职责

| 角色 | 承担方式 | 职责 |
|---|---|---|
| 安全负责人 | 已确认的项目负责人 | 核验对外请求、确定最小交付范围与接收对象、记录批准或拒绝、协调异常与归档策略 |
| 查询与导出管理员 | 所有有效管理员，按 C-08 | 内部查询和导出；核对实际范围、完备性与审计；承担已确认的对外交付操作时按下文记录 |
| 内容审核与投诉处理 | 团队开发者同时担任管理员，共同运营 | 通过现有网站反馈入口受理，收到投诉即处理；逐条处置、保存处理依据，必要时通过现有飞书群沟通 |
| 运维与档案保管 | 服务器由另一开发成员维护；备份承担人与口令持有人未确认 | 在受控主机取得入口日志、验证文件哈希与权限、维护归档及故障记录；备份保管与恢复安排按实际记录核验 |

上述角色说明职责边界，按 C-20 由团队共同承担，不要求另建逐人分工、排班或成员名单。未结事项按实际需要在受控记录中交接，必要时在现有飞书群确认接手；不把密码、Cookie、token、备份口令或日志原文写进公开仓库，不因此新建账号或改变无关管理功能权限。备份可能由服务器维护成员承担，但目前未确认，不能据此写成既定事实。

**内部查询导出与对外提供资料分别管理。** C-08 允许所有有效管理员内部查询和导出，不需要负责人逐次批准才能点击导出；未登录者、普通用户及失效管理员仍须被后端拒绝，成功、失败和拒绝保留适当审计。对外提供资料时才走主体、文书、经办人、依据、最小范围、批准和接收确认流程，不用本规程给导出按钮新增审批门槛。

## 二、内容处置、投诉值守与异常升级

1. 私密投诉举报可匿名受理，始终不公开；有登录身份的提交人可通过本人入口查看允许返回的处理回复，不能因此让其他用户或公众取得原文。
2. 用户确认现行做法为团队通过现有网站反馈入口收到投诉即处理；管理员在后台「反馈与举报」逐条核对，保留受理时间、条目编号、实际操作者、处理状态及必要依据，未结事项按需沟通和交接。使用现有单条处置、回复和隐藏/撤销公开能力；处理完成与允许公开分开，不能将投诉改类或标记完成后公开。本候选未交付批量处置、合并或条目删除，不以人工记录声称已有这些能力。
3. 课程评价延续既有自动规则：`moderationRequired=true` 或命中已启用的检测规则时待审，其余按规则自动公开并留实际依据，可事后下架。新普通反馈默认待审，须管理员显式批准才公开；处理完成、回复、取消隐藏不授予公开资格。历史实际公开的内容与公开回复按 C-14 保留，不补造旧人工审核；未公开、隐藏、私密或已撤销内容不因此公开。必要封禁使用现有账号管理能力，核对下一请求的实际拒绝结果，不凭按钮显示宣称已生效。
4. 疑似资料泄露、凭据泄露、超范围请求、无法可靠核验主体、持续日志故障或其他无法由当前处理人解决的事件，按已确认做法由团队开发者必要时通过现有飞书群沟通，并交安全负责人统筹。交接记录包含发现时间、事项编号、影响、已采取动作、待办、接手角色及确认时间，避免转发投诉全文或秘密。
5. 「收到投诉即处理」是用户确认的现行做法，不据此编造固定响应时限或全天值班事实；需继续跟进时记录实际下一检查/处理安排。合成演练与真实处理记录分别保存，不因已有规程而声称处理过真实案件。本轮不重新接通通知，不发送真实测试或群消息；用户此前称通知接通过，不作为新增用途的送达证据。

软件的管理员审计、用户事件与条目处理元数据保留实际操作者/目标/时间/结果；遇到写入失败或结果未知，先核对业务记录和恢复队列，不能用手写成功记录替代缺失的技术证据。

## 三、对外资料协助与受控交付

用户已确认对外资料核对与发送由团队开发者承担；这只确认现行职责，不证明已执行真实公安案件。逐步操作、登记字段、入口日志取数和离线演练见 [S4 受控交付操作单](compliance/S4_CONTROLLED_DELIVERY.md)。基本顺序为：

1. **登记与核验：** 登记请求编号和收到时间，在私密档案保存主体、文书、经办人及依据材料；负责人通过可确认的渠道核验真实性、适用范围与接收对象。来源 IP、账号关联或一份自称公函不能单独证明真实身份或请求有效。
2. **范围与决定：** 写清账号/内容选择条件、时间及边界、站点、数据来源、必要字段，确定最小范围；记录批准或拒绝及理由。主体不明、依据无法确认或请求超范围时不向其提供资料，留存拒绝/补正记录。
3. **受控取数：** 有效管理员内部查询/导出；记录查询/导出审计事件、候选版本、筛选条件、各类数量、完备性与已知限制。必要的入口网络日志由受控运维流程取数，无需塞进后台同一页面。超限失败不能当作已得到完整导出，缺失或部分结果不能写「全部」。
4. **交付前复核：** 对照批准范围逐项去掉无关账号、内容、字段和凭据。留存源导出哈希与最小化处理记录，对最终文件重新计算 SHA-256、字节数及记录数，负责人确认限制与交付对象；文件变化后重新复核并计算哈希。
5. **交付、接收与归档：** 仅按已确认的对象及受控方式提供最终文件，记录方式/时间/经办/传递凭证；取得同一文件哈希的接收确认后才登记完成。未确认、哈希不一致或对象变更时保持待处理，不能伪造确认。文书、核验、决定、范围、来源/审计、最终文件与确认一并私密归档，登记保管人、访问边界与适用保留策略。

归档保留策略由负责人结合真实请求及数据分类决定并记录依据；尚未确认的期限明确待定，不在此新增固定法定期限，也不缩短已经实施的日志保留。内部数据、原始日志、完整导出、秘密、文书与真实登记不得上传公开站点、资源桶、公共 PR 或聊天。

## 四、日志留存与边界

- S2 用户安全日志与入口日志的现有软件配置按 400 天保留；Caddy 模板为 `9600h`，关闭数量淘汰，私密归档按最新记录时间清理。这是当前配置事实，不是本文件对适用法定期限的解释；实际生产启用、容量、可恢复性及缺口仍须以对应部署回执核验。
- 管理员审计与调取记录包括 SQLite、补写队列和私密归档；查询到的最近一页不是全部留存记录，须按范围与分页/完整导出核对。归档不是删除，不能因前台只显示部分记录推断其他记录已丢失。
- S2 入口档案保留时间、站点、方法、路径、状态、可得来源/连接字段及单独保留的 UA；查询串和请求/响应头被脱敏删除，不能事后还原被删除的值。journald 运行日志不应再成为未脱敏的第二份访问日志。真实来源端口只有实际可得时填写，上游代理端口不能冒充用户端口。
- Caddy 的 IP 是网络来源信息。可信代理配置、上游拓扑和当时记录决定 `client_ip` 能否解释为客户端来源；IP、UA、账号关联均不等于经过核验的自然人身份。缺失字段、未知拓扑或日志空档须明确记录，不补造。
- SQLite、运行 JSON、队列、归档及必要秘密/配置的完整备份沿用私密加密流程，不含课程文件/头像对象字节；公开资源桶不接收此类资料，私密 R2 当前未启用。日志与加密备份保持既有 400 天工程配置，不因本轮运营确认而修改。D-01 已按 C-17 确认为保留内容、清理身份及业务关联，不再重复询问内容取舍；课程评价、普通反馈和私密投诉尚未约定统一保留期限，不能推断永久保留。各类资料的保留依据及实际到期处理、备份承担与口令保管、独立注销账本灾备仍需分别落实与核验。

## 五、账号认证与资料用途

- 公开投稿须登录、完成手机号认证且未被封禁；匿名浏览公开资料允许，私密投诉举报可匿名。不能继续写「所有举报必须实名」。
- 后台账号数据可包含手机号、OpenID、认证时间等信息；普通用户接口按其实际字段与掩码规则返回，有效管理员受控查询/导出可能取得原始信息。这些信息不因具备查询权限就成为可公开资料。
- `user_id` 与手机号/OpenID、发布条目及安全事件的关联用于站内账号追溯。微信手机号认证、账号关联与来源 IP 不能被描述为已完成经办人/自然人的法律身份核验；对外请求仍按第三节独立核验。
- 账号资料还包含头像、可选邮箱、收藏、密码摘要和注册/登录元数据；正文、联系方式、支付昵称/备注、日志和历史备份各有不同用途及访问边界，不能写“不记录手机号/原始 IP”或“所有数据已匿名化”。公开昵称/正文的自动检测范围与启用配置有限，值守人仍须处理相关投诉；不能宣称全部文本已自动检查。
- 普通用户 Bearer/网页会话默认绝对期限为 30 天，扫码票据 5 分钟；当前服务入口的管理员会话默认绝对和空闲期限均为 7 天，可分别配置。类自身 8h/30min 默认值不能代替入口或生产实际环境的配置回执。

## 六、注销、身份清理与保留例外

执行 [S5 策略](compliance/S5_POLICY.md)和[S5 运维说明](compliance/S5_OPERATIONS.md)：停用账号、撤销全部凭证与扫码票据，清 OpenID/密码摘要/手机及认证状态/邮箱/原昵称/头像地址/收藏。评价、反馈、私密投诉的原文、回复和原可见性保留，业务账号关联、联系方式、直接身份副本及本人投票清理；私密投诉继续私密，注销后无法通过原账号查看回复。

保留必要订单/交易/金额/支付状态，清业务身份、昵称和备注；公开捐助昵称按精确订单键清理，无键历史记录人工核对。受限历史审计可能仍关联内部编号；最小独立注销账本和作业保留账号实例、规则版本及必要处理键用于中断恢复，不含原昵称、手机或凭证。这些记录不是彻底匿名；正文自述信息不承诺自动消除。

仅 `200` 且 `deleted=true` 表示当前必要清理完成；`202/pending` 只是已受理并停用，远端失败或未知上传须继续重试/核验。源站头像删除不能证明旧缓存或第三方副本消失。历史加密包不逐份改写，恢复须保持隔离，使用独立最新账本重放并验证；不能直接回退不识别账本的旧代码，不能凭备份内水位证明最新性或启用旧身份。

## 七、已确认运营事实与后续验收边界

| 事项 | 已确认事实及仍需留下的实际记录 |
|---|---|
| 公司主体与联系范围 | 公司资料已有受控原PDF及用户记录；正式联系人为负责人本人，申报仅 `nkustudy.top`。不再索取电话或成员名单；正式字段在私密材料核对，敏感主体字段不进公开Git |
| 投诉处理与异常沟通 | 团队开发者兼管理员共同运营，通过现有网站反馈入口收到投诉即处理，必要时飞书群沟通；不要求另建逐人值班表。实际受理、处置及需交接的事项留记录，不把用户确认当作具体案件的执行凭证 |
| 分类保存与到期处理 | 课程评价、普通反馈、私密投诉未约定统一期限；业务资料、支付事实、受限日志、最小账本/作业、案件档案及历史备份分别登记依据、期限或待定项、清理及复核角色；保持日志/备份既有400天工程配置，不推断永久保留或新增法定期限 |
| 服务器与备份保管 | 服务器由另一开发成员维护；备份可能同人承担但尚未确认，口令持有人也未确认。实际备份保管、独立解密、最新注销账本来源及独立灾备仍待核验，不要求向聊天提供口令 |
| 对外交付实际执行 | 团队开发者承担核对与发送；有真实请求时记录主体/文书/经办/依据核验、最小批准范围、私密文件权限与哈希、传递及同文件接收确认。内部导出和职责确认不等于已交付，不编造真实公安案件 |
| 最终候选生产事实 | S3 迁移及公开数量、私密投诉隔离、S4 完整取数/落盘、S5 最新账本及恢复、真实头像/缓存、自定义隐私文案、入口日志窗口/容量和私密远端读回 |

这些现实决定和回执不阻止已能核对的本地文档修正，但不能因规程、合成演练或本地回归完成而将 GOV-16、DOC-18 或全部整改自动标为生产已验。
